### 段階1 — 回答・報酬の保存契約を揃える

対象: S1→S2→S3。初回識別子を回答確定前に作り、再送時は同じIDと内容を保持する。別の新しい回答には別IDを与える。同じIDに異内容が届いた場合はwrite前に拒否する。

履歴と学習eventはreceiptと同じcommitへまとめる。弱点/KPI等の再構築可能な投影は、遅れ・失敗・再構築状態を記録する。報酬の正本はサーバーに置き、同じ学習sessionの結果を読み直せるようにする。学習保存と報酬反映は別状態として保持する。

受入条件:

- 同じID・内容を並行で送っても1回答1履歴更新1event1報酬。receiptの応答も同じ結果。
- commit後に応答を失わせ、その後の再送で増加しない。
- 履歴保存後・event前の障害を注入して、全rollbackまたはreceiptから回復できる。
- 同じID・異内容は409等の明示的な失敗になり、追加writeがない。
- 異なる回答の同時保存は失われず、同一語の競合に明確な結果がある。
- 最終問題・途中離脱・戻る・連打で画面得点と保存済み回答がずれない。
- Cloudflare/D1で保証する。IDBにも提供する経路だけ、native IDBのtransaction回帰を別途確認する。

既存 [quiz-controller tests](../../tests/quiz-controller.test.ts)、[English practice tests](../../tests/english-practice-progress.test.ts)、API runner、保存receipt回帰を拡張する。文字列や実装形状に合わせたテストではなく、障害後の永続行数と再送結果を検証する。

対象: O1→O2。まず管理者の部分取得失敗を局所化する。資源ごとの未取得・0件・更新失敗・最後に確認した値を持ち、別アカウントの遅い応答や過去refreshが現在の画面へ入らないようにする。

実操作:

1. 管理者がクラス・担当を決め、課題を配布する。
2. 生徒がホームから対象課題を開始し、学習・提出を保存する。
3. 講師が担当生徒の提出を見つけ、確認して返却する。
4. 生徒が返却物を見つけ、修正または次の学習を開始する。
5. 管理者が未処理箇所と次の行動を判別する。

受入条件:

- 上記を手動SQLなしで完走し、各段階の証拠を残す。
- 一資源が500になっても、他の確認済み情報と可能な担当操作を使える。該当資源だけ失敗・再試行を示す。
- 並行refresh・アカウント変更後の遅延応答は表示されない。
- 担当外/別組織生徒・課題・返却物へのGET/POST/PATCHがサーバーで拒否される。
- 「通知保存」「既読」「通知後の再学習」を区別する。外部到達や効果を通知作成数から推定しない。

合成データの完走は運用可能性の証拠であり、実教室の利用率の証拠ではない。本番確認は権限と扱えるデータ範囲を確定した別工程にする。

### 段階3 — AI・認証の境界を補強

対象: A1/A2。高コスト処理前に処理単位をclaimし、lease期限・回復・結果取得を定義する。AI予算は同時要求を含めて予約し、実行後に精算する。認証rate limiterとpassword resetは別のレビュー単位にする。

受入条件:

- 同一Writing attemptへの同時finalizeでprovider呼出しは1回、提出も1件。
- claim所有者の停止後は期限と明示状態に基づき回復し、永久に処理中にならない。
- 提出commit後のanalytics失敗で「未保存」と表示しない。再取得で確定結果を表示できる。
- 予算残り1要求分で同時要求を送っても受理合計が予算内。失敗・timeout・lease切れの予約が回復する。
- 5件等の並行認証失敗でカウント更新を失わない。仕様に沿ってIP・identity別の攻撃を検証する。
- password resetの各writeに障害を入れ、token消費のみ・旧session有効の半端な状態を残さない。再送/二重使用は定義どおり拒否する。

fixture providerで呼出し回数を測定し、この調査のために実AIへ教材・答案を送信しない。

### 段階4 — 学習の成果と教材品質を確かめる

対象: L1/L2。先に「graduatedでも期限が来たら復習するか」を決める。状態名、復習選択、due数、課題判定、Cloudflare/IDBの一致を一つの変更として扱う。既存履歴の一括消去や再評価は行わない。

受入条件:

- 合成履歴の新規/学習中/復習中/定着済みを、期限前/当日/期限後で検証する。選択・表示・due数が同じ方針を使う。
- 長期復習を導入する場合、1日の負荷上限と新出・期限超過の優先順位を定義し、一度に大量の既存語を返さない。
- 自己評価に基づく進捗と、採点された想起テストの正答率を表示・指標上で区別する。
- 1冊の対象教材から難度・品詞・多義語・例文・訳の種類を分けた固定golden setを作る。期待解答、許容解答、非許容解答、判断理由、教材version、確認者を記録する。
- blank/sentinel/出典coverage等の既存QAに加え、誤訳、不自然な例文、単語と文脈の不一致、正答以外も正しい選択肢を人が確認する。全件レビューを実施していない場合は対象数と未確認範囲を示す。
- AI採点は代表答案と許容言い換えで比較し、false positive/false negativeと採点根拠を残す。平均一致率だけで通さない。

効果を観測する場合は、初回に解いた語を固定して7日後等の遅延想起を確認する。対象人数、語数、継続観測できた割合、試験形式、教材/課題versionを添える。継続率と学力効果は別指標。少数の試行を因果効果の証明にしない。

### 段階5 — 最新画面を測定して利用障害を減らす

対象: U1。別の隔離runtimeを提供された後、以下の実測を行う。録画中の41812/41828/41838/41848/41858/41868のruntimeおよび動画用ブラウザは触らない。合成アカウント・合成教材だけを使う。

| 領域 | 確認条件 | 受入条件 / 記録 |
| --- | --- | --- |
| 学習開始 | 生徒ホーム、課題あり/なし、返却あり、教材なし、取得失敗 | 主行動の表示と遷移が一致。初回1冊の開始に不要な設定を要求しない |
| 情報量 | 390pxスマホ、1280px PC、844×390横向き、200%ズーム | 主行動を探す時間・同等CTA数・最初の画面の文字数を記録。必要な情報と操作が隠れない |
| 日本語 | 生徒/講師/管理者の入口・空状態・失敗・保存・完了 | 未取得を0と読ませず、「何が起きたか・次に何をするか」がわかる。技術語は利用者の判断に必要なものだけ |
| 入力 | スマホキーボード表示、和訳/英作文、長い教材名/生徒名 | 固定バーが入力・送信を覆わず、縦横でページ全体の横overflowなし |
| キーボード | 学習開始→回答→保存失敗→再試行、一覧→dialog→閉じる | Tab順序・可視focus・戻り先が自然。hiddenカードの操作にfocusが入らない |
| 読み上げ | VoiceOver等で同じ経路、状態更新、modal重なり | 問題・選択・保存状態が読める。背景の不要操作や重複読み上げを確認。未実施なら未検証と記載 |
| タッチ/表示 | 密度・文字サイズ設定、低い画面高、safe area | 主要操作をタップでき、文字拡大で欠けない。各対象の実寸を測る |
| 回復 | offline、API500、commit後の応答消失、再ログイン | 記録の確定状態を保持し、保存されていない回答を完了と表示しない |
| 性能 | 同じ端末条件・fixtureでcold/warm開始を各3回、画面別network | JS transfer、LCP、長いtask、開始/再試行時間、API p50/p95を記録。遅延原因をUI/API/AIに分ける |

性能の暫定受入条件は、主要操作に200ms超の同期処理による停止がなく、確認済み操作の所要時間が同条件baselineから20%以上悪化しないこと。これは本番SLOではなく初期回帰線。母数のないp95や、3回の値から本番品質を断定しない。bundleの一律KB上限はbaseline取得後に設定する。

改修は実測された行き止まり・操作不能・誤認を先に扱う。全画面を同じ装飾に揃えることや、日本語全文を一度に書換えること自体を受入条件にしない。

### 段階6 — 保守性を段階的に改善

対象: M1。まずquizのattempt処理、英語演習lane、取得resource、表示コンポーネントを抽出する。DB契約と保存保証を分割と同時に大きく変更しない。サーバーAI処理は入力検証・provider呼出し・費用・監査の責務を明示する。

受入条件は公開サービス契約の同値、保存・認可回帰、依存境界・循環gate、移行した旧経路の参照0。削除候補はsource reachabilityと実参照で判断し、教材・DB・録画・固有成果物・未追跡ファイルを古いという理由で削除しない。

全面再構築を検討する条件は、保存や認可の契約を局所的に分離できず変更が繰り返し同じ重大障害を起こす、主要操作の行き止まりが共通構造に起因し局所修正で解消しない、または実測性能で分割済み構造が継続的に予算を超える場合。現時点ではその証拠が揃っていない。仮に再構築する場合も教材ID・履歴・権限・migrationを保ち、1フローごとに置換して旧経路と結果を比較する。
